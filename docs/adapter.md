# Internal conformance adapter protocol v1

The replacement does not exist yet. Implement this adapter as a thin wrapper around its real wallet functions. Keep implementation logic out of the adapter. The adapter is a testing seam and is independent of the production CLI.

The harness starts the supplied executable directly with optional `--adapter-arg` arguments. Each invocation gets one newline-terminated JSON request on stdin and must return exactly one JSON object on stdout before exiting successfully. No shell is involved. Stderr is discarded to prevent secret leakage into reports. The default deadline is ten seconds and stdout is limited to one MiB. Unsupported operations fail; they cannot be reported as successful skips.

```json
{"protocol_version":1,"id":"case-id","operation":"ed25519.sign","input":{"seed_hex":"…","message_hex":"…"}}
```

```json
{"protocol_version":1,"id":"case-id","result":{"public_key_hex":"…","signature_hex":"…"}}
```

```json
{"protocol_version":1,"id":"case-id","error":{"code":"invalid_input"}}
```

Return exactly one of `result` or `error`, with the same ID and protocol version. Error results in exact vectors compare exactly; map implementation-specific errors at the adapter boundary. Hex is lowercase, even-length, without `0x`. Quantities are JSON integers, not floating point. Paths are arrays of unsigned 32-bit indices; hardened indices include bit 31. Do not treat BIP39's seed-generation PBKDF2 as Cardano's Icarus root-generation PBKDF2.

Encrypted-root component profile (cardano-crypto-wallet 0.2.0.0): `root-key.parse` accepts `key_hex` and returns `format` (`v1`/`v2`) and `xpub_hex`. `root-key.create-v2` accepts `master_key_hex` (96-byte plaintext extended key), `passphrase_hex` and `randomness: "counter-v1"`. `root-key.check-v2` accepts `key_hex`/`passphrase_hex` and returns `valid: true` or a backend error. `root-key.sign-v2` adds `message_hex` and returns `signature_hex`/`xpub_hex`. `root-key.change-v2` takes `key_hex`, `old_passphrase_hex`, `new_passphrase_hex` and the randomness profile. `root-key.derive-v2` takes `key_hex`, `passphrase_hex`, `path` and the randomness profile; derivation is scheme 2. Create/change/derive return `key_hex`, `format`, `xpub_hex`. Errors use the exact named `XPrvError` constructor in `code`, mapped explicitly by other-language adapters. The counter profile resets for each request; salt consumes counter 0 and nonce counter 1, with further encryptions consuming the next counters. Byte generation repeats the eight little-endian counter bytes, truncated to the field length. Production Argon2id parameters are mandatory. This deterministic entropy profile is solely for test fixtures. Parsing a V1 key is distinct from authenticating it; V1 wallet-level unlocking and migration remain separate obligations.

`wallet.credentials` measures wallet-level database transitions. Inputs are `flavor` (`shelley`, `shared`, `byron`, `icarus`), `mnemonic` word array, `scheme` (`pbkdf2` or `scrypt`), `initial_format` (`v1`, `new` or `none`), `passphrase_utf8`, `password_probes` (strings), `message_hex`, `randomness: "counter-v1"`, and `actions`. An action is `{"type":"unlock","passphrase_utf8":"...","callback_error":false}` or `{"type":"change","old_passphrase_utf8":"...","new_passphrase_utf8":"..."}`. `new` calls normal credential attachment and requires PBKDF2-prepared input; the wallet chooses the stored format by flavor. The result contains an `initial` credential snapshot and ordered `steps`. Snapshots expose format, scheme, encrypted-key bytes, extended public key, hash presence and password-probe acceptance, but no raw password hash or clock timestamps. Steps include outcome, callback access/signature (unlock only), post-action snapshot, and exact credential/key-byte/metadata/timestamp equality against the pre-action state. Root signatures are checked independently. Callback failure is deliberate: successful migration happens before the callback and can persist even if the callback fails. Fixtures use a real isolated in-memory wallet database; this profile does not establish disk restart/crash durability.

The fixtures are the authoritative request/result shapes for these operations. All keys and mnemonics in the committed corpus are public test material. Returning private values is permitted only across this test adapter for known fixture inputs; reports do not log them.

A selection request contains `utxos` (each with unique `id`, `eligible`, and `value`), requested `outputs`, a fixed `fee`, `minimum_change_coin`, `maximum_inputs`, and an explicit `seed`. A bundle is `{ "coin": 10000000, "assets": { "policy_hex.asset_name_hex": 7 } }`. Omitted assets mean an empty map. The result identifies selected inputs by their exact fixture IDs and returns change bundles. Requested outputs cannot be modified. Fee in the result must match the supplied fixed fee. This adapter tests the selection component under fixed external constraints; ledger-dependent fee estimation is a separate requirement.

The verifier requires unique eligible inputs from the supplied set, bounded input count, minimum change ADA, and exact ADA and native-asset conservation using wide integer totals. It repeats seeded selection requests and requires identical results. Impossible-value fixtures expect `{ "error": { "code": "not_enough_money" } }`. These constraints allow multiple valid strategies. They do not establish exact compatibility with the Haskell selection strategy; `selection.seeded-oracle` remains a separate mandatory requirement.

The current transaction inspector independently parses definite-length Shelley-family CBOR and checks transaction body hashes and all vkey/bootstrap signatures. It requires actual ledger submission as additional evidence; it is not a complete ledger implementation and does not yet cover all valid Byron, script and indefinite CBOR forms.

Additional adapter operations for transaction construction, fees/min-UTxO, scripts, discovery, block application/rollback, persistence and governance require independent vectors and contracts before their catalogue requirements can pass. Their absence is explicitly reported by the exhaustive gate; this document does not imply that those tests are already implemented.

`keys.sign-extended` takes `xprv_hex` in the 96-byte extended-secret-plus-chain-code representation and `message_hex`, and returns `public_key_hex` and `signature_hex`. Its pinned Haskell metadata-signature golden is additionally verified with the independent Ed25519 verifier. `fixtures/http-signatures.json` exercises the same golden through the public binary signature endpoint and verifies it against the HTTP-derived key.

`passphrase.check-pbkdf2` and `passphrase.check-scrypt` take `passphrase_utf8` and the complete serialized stored `hash_hex`, returning `{ "valid": true }` or `{ "valid": false }`. Wrong passwords and well-formed hex encoding of malformed stored hashes return false according to Haskell behavior; malformed hexadecimal input returns `invalid_input`. These operations call actual wallet password checking functions, including legacy scrypt's password preparation and CBOR handling. Scrypt-to-PBKDF2 key migration remains a separate unimplemented obligation.

`keys.verify-extended` takes `xpub_hex` (64-byte public key plus chain code), `message_hex` and `signature_hex`, returning `{ "valid": boolean }`. The reference driver calls `Cardano.Crypto.Wallet.verify`, the verifier used by the Haskell metadata-signature integration test, through `xpub` and `xsignature` decoding. This is a distinct compatibility seam from RFC-oriented `ed25519.verify`; backend acceptance at low-order/noncanonical boundaries must be captured from the actual wallet verifier before expectations are frozen. A probe of a general-purpose crypto library alone is insufficient evidence of wallet behavior.

The pinned `cardano-crypto 1.3.0` wallet-verification profile accepts a canonical signature with scalar `S + L` and the identity-point public-key/signature pair. Reference probes through the directly compiled pinned wallet source and its declared backend confirm this behavior. `keys.verify-extended` preserves those compatibility results explicitly; it must not be silently replaced with a stricter verifier. Strict verification used by the harness to inspect real transaction witnesses remains separate and is additionally checked by ledger submission. These observations do not assert that a node will accept such a transaction witness. A future authoritative specification can change the verifier profile only through an explicit reviewed version change.

`coin-selection.haskell` tests the pinned Haskell `Balance.performSelection` component with strategies `minimal` and `optimal` (default `optimal`). Inputs contain the existing `utxos`, `outputs` and u64 `seed`, plus `minimum_fee`, `minimum_change_coin`, optional `maximum_output_coin` (default45,000,000,000,000,000), `maximum_output_token_quantity` (default2^63-1), and positive `maximum_assets_per_bundle` (default32). The supplied callbacks use a constant minimum fee, constant minimum ADA and asset-count bundle-size assessment; this explicitly scoped component profile does not establish ledger-dependent fee/min-UTxO or collateral conformance. Outputs must already satisfy those external limits. Seeds are converted to signed two's-complement 64-bit values for System.Random `mkStdGen`; the exact RNG/library versions belong to oracle provenance.

The result contains `inputs` in Haskell order, ordered `change` bundles and the actual `fee`. Fee may exceed its minimum when the Haskell component absorbs ADA dust, bounded by its maximum-cost rule; this differs from `coin-selection.select`'s fixed-fee invariant interface. Structured errors use `empty_utxo`, `balance_insufficient` (available/required/shortfall bundles) or `unable_to_construct_change` (required_cost/shortfall coins). The generic fixed-fee interface uses the same component but normalizes insufficient-value errors and requires the fixed fee/input limit after selection. Neither interface reimplements the selection algorithm in the reference driver.

Observed ADA-dust correction: the pinned `assignCoinsToChangeMaps` explicitly discards a final empty asset map when the remaining ADA cannot fund its minimum output. With a200,000 minimum fee and1,000,000 minimum change, a2,800,000 input paying2,000,000 yields no change and an800,000 actual fee. Thus the component's generic twice-minimum-cost postcondition is not a universal bound for this callback profile. The independent verifier permits empty-change fee excess strictly below `minimum_change_coin`; it rejects burning ADA that could fund change. Native assets must still be conserved and cannot be discarded as ADA dust.

The ADA maximum is the sizing/global-supply bound used by the pinned component, not an instruction to partition ADA into arbitrary smaller outputs. Eligible input ADA must fit that budget. Coin-only change distribution is tested with multiple requested outputs; native-token quantity and asset-count splitting use the component's actual splitting functions. Wide arithmetic fixtures keep ADA within the ledger supply bound while native-asset totals span more than64 bits.

The `keys.derive` wallet-path profile accepts an empty root path, a three-index hardened account path, or a five-index address path whose role is0,1 or2 and whose address index is soft; Byron also accepts its two-index legacy path. Indices are exact unsigned32-bit integers. Public derivation accepts only soft indices. Unsupported styles, malformed mnemonic/key encodings, malformed paths and index overflow return `invalid_input`. This validation bounds the test adapter domain; the underlying low-level scalar derivation functions may accept additional index sequences. For root/private goldens, the test encryption password is empty. `second_factor_hex` is a generation factor, not that encryption password; nonempty factors require separately supported flavor semantics and observed vectors.

`bip39.wallet-seed` takes `mnemonic` and `passphrase` strings and returns `seed_hex` from the pinned Haskell `Crypto.Encoding.BIP39.sentenceToSeed` helper without external normalization. This explicit component profile is distinct from standard `bip39.to-seed` (NFKD). `keys.generate-root-profile` takes `style` (`Shelley`, `Shared`, `Icarus`, `Trezor`, `Ledger`), mnemonic sentence, generation `second_factor_hex`, wallet `encryption_passphrase_utf8`, and a bounded `path`. It returns unencrypted96-byte `xprv_hex`,64-byte `xpub_hex`, and the128-byte legacy `encrypted_xprv_hex`. Ledger accepts no generation factor in the actual wallet helper; Trezor's wallet route uses Icarus generation. Nonempty Icarus/Trezor factors name the low-level cardano-address generation profile, not an HTTP feature. Shelley/shared factors must encode supported mnemonic entropy. The encrypted wallet representation is retained to observe Unicode encryption-password behavior.

The root-profile input also includes `message_hex`; the result includes `signature_hex` made by the actual derived child key. Rust independently verifies it against the returned public key. This binds each captured hardware/factor key to a real signing operation as well as its exact serialized bytes.

For the standard seed profile, the Rust `haskell-mnemonic-reference` transport wrapper applies NFKD only to `bip39.to-seed` inputs, then delegates to the Haskell raw-seed helper. It accepts the Haskell executable as its sole argument. Other operations, including `bip39.wallet-seed`, pass through unchanged. This explicit test-boundary normalization preserves both behaviors and does not claim that the pinned Haskell helper normalizes on its own. Frozen published/OpenSSL Unicode goldens remain the independent expected answers.

Address/script component operations use the following explicit shapes. `native.script` takes recursive `script` objects with `type` (`signature`, `all`, `any`, `at_least`, `before`, `after`), `key_hash_hex`, `scripts`, `required` or `slot` as applicable, plus `signers` (28-byte hash strings), `invalid_before` and `invalid_hereafter` (nullable u64). It returns `cbor_hex`, `hash_hex`, `satisfied` from the ledger evaluator, and `valid` from required structural validation. `address.build` takes `network_tag`, `kind` (`base`, `enterprise`, `pointer`, `reward`), payment/stake credentials (`type:key` with `hash_hex` or `type:script` with `script`), and optional pointer fields `slot`, `transaction_index`, `output_index`; result is `address`, `address_hex`. `address.byron` takes `style` (`Byron` or `Icarus`), mnemonic sentence, account/address indices and network (`mainnet` or `preprod`), returning base58/address bytes. `address.inspect-byron` validates address bytes including their CRC through the actual inspector. `byron.path-encrypt` takes32-byte `passphrase_hex`, u32 `account_index`/`address_index`, returning `attributes_hex`; `byron.path-decrypt` takes the password and attributes, returning nullable `path` or an input error as observed from Haskell. Codec operations `encoding.bech32` and `encoding.base58` take `action` (`encode`/`decode`), `bytes_hex`/`text` and Bech32 `hrp`, returning encoded text or decoded bytes/HRP. `governance.identifier` takes `action`, role (`drep`, `committee_hot`, `committee_cold`), kind (`key`/`script`) and hash bytes or text. `asset.fingerprint` takes28-byte policy and0–32-byte asset name, returning the actual wallet fingerprint. `key.hash` hashes a32-byte public key through the actual credential-hash helper. These component tests do not replace the separate cross-network HTTP rejection and real transaction/ledger obligations.

The Haskell script serializer's `native.script.cbor_hex` includes its leading native-script domain byte `00` followed by canonical script CBOR. `hash_hex` is BLAKE2b-224 of that complete domain-prefixed serialization. This is distinct from a CBOR item containing the script alone.

A wallet.credentials unlock action can request `fail_migration:true` to exercise the actual backend-failure branch on an authorized modern V1 wallet. The reference oracle arms a one-shot Argon2 FFI fault immediately before actual withRootKey; ordinary calls delegate to the original backend unchanged. Injected steps additionally return `migration_faults_consumed`, `migration_warnings`, and `production_kdf_parameters`. Exactly one fault and the actual wallet warning must be observed, with V1/metadata preserved and the callback still usable. The next non-injected unlock must retry migration. Unsupported or unconsumed injection is a failed fixture, never a passing skip. This test-only adapter capability is required for the internal conformance profile, not a public HTTP feature.

`transaction.roundtrip` takes `era` (`byron`, `shelley`, `allegra`, `mary`, `alonzo`, `babbage`, `conway`, `dijkstra`) and `cbor_hex`; it returns the actual wallet reader/renderer `cbor_hex` and `transaction_id`, or `decode_failed` for a valid-hex decoder failure. Captured fixture transactions are structurally representative codec inputs, not claims of ledger-valid UTxOs or signatures. `metadata.encode` takes `ledger_version` and `entries` (u64 `label`, recursive `value`); value types are `number` (`value` integer), `bytes` (`hex`), `text` (`value`), `list` (`items`), and `map` (`entries` of `key`/`value`). Result is actual wallet `valid`, plus ledger `cbor_hex` when valid or structured `errors` when invalid. Integer values use the wallet's symmetric range ±(2^64−1); text is bounded by UTF-8 bytes. `ledger.ed25519.verify` takes32-byte `public_key_hex`, `message_hex`,64-byte `signature_hex`, returning the actual ledger DSIGN acceptance boolean, including malformed-length handling. This seam remains distinct from keys.verify-extended and its historical permissive profile.

`fee.components` takes u64 `transaction_bytes` (excluding witness estimates), `vkey_witnesses`, `bootstrap_witnesses`, `coefficient`, `constant`, `maximum_transaction_bytes`, `execution_memory`, `execution_steps`, and rational `memory_price`/`step_price` objects (`numerator`, positive `denominator`). Return actual component `vkey_witness_bytes`, `bootstrap_witness_bytes`, `estimated_bytes`, `linear_fee`, `execution_fee`, `total_fee` and `within_size_limit`. This estimates component cost with the wallet's conservative witness formulas; real ledger acceptance, exact signed transaction fees and reference-script tier fees remain separate. `minimum-utxo` takes canonical Conway `output_cbor_hex` and `coins_per_byte`; return `minimum_coin`, `wallet_minimum_coin`, `below_minimum`, `output_cbor_hex` and `wallet_output_cbor_hex` (coin replaced with the wallet maximum). These are actual ledger and wallet helper results, not interchangeable minimum estimates.

The writer component uses `witness.build`/`witness.sign` with `transaction_cbor_hex`, `xprv_hex` (wallet legacy128-byte serialization), `passphrase_hex`, `style` (`Shelley`/`Byron`), `address_hex` and optional testnet `network_magic` (null means mainnet). Build returns serialized `witness_cbor_hex`; sign returns actual wallet `transaction_cbor_hex`, preserving existing witnesses. The capture corpus contains public test credentials only. `wallet.certificates` takes `era` (`conway`/`dijkstra`), `stake_xpub_hex`, optional `stake_script` (native signature key hash), `action` (`join`, `join-registering`, `quit`, `vote`, `vote-registering`), nullable `deposit`, `pool_hex` and `drep` (`abstain`, `no-confidence` or key/script hash). Return serialized `certificates_cbor_hex` array. Actual documented wallet exceptions map narrowly to `unsupported_era` or `deposit_required`; malformed requests return `invalid_input`. Real ledger submission and state changes are separate requirements.

`witness.script` takes `script_key_hash_hex` (28 bytes), converts the actual native signature script, and returns `witnesses_cbor_hex` for its Conway ledger witness set plus `script_hash_hex`.

`selection.wallet` takes `utxos` (u32 `id`, u64 `coin`/`asset_quantity`, boolean `inputs`/`collateral` availability), `outputs` (coin/asset_quantity bundles), `minimum_fee`, `minimum_change_coin`, `maximum_collateral_inputs`, `collateral_percentage`, boolean `collateral_required`, `mint_quantity`, `burn_quantity`, u64 `seed` and `strategy` (`minimal`/`optimal`). Asset quantities refer to a fixed public policy/name and all fixture addresses are fixed public key enterprise addresses. Results contain selected `inputs`/`collateral` IDs, `change`, `outputs` and actual `fee`; errors preserve actual `empty_utxo`, `balance_insufficient`, `unable_to_construct_change` or `insufficient_collateral` (including `minimum_collateral`, `largest_available` IDs). Minimum-fee/change callbacks are explicitly constant component constraints; this does not replace node protocol or balanceTx admission tests.

`transaction.minimum-fee` takes Conway `transaction_cbor_hex`, u64 `coefficient`/`constant`, rational `memory_price`/`step_price`/`reference_script_price` objects (`numerator`, positive `denominator`), `reference_script_bytes` (bounded200000 for this profile) and `execution_units` (at most16 memory/steps pairs). Nonempty execution_units replaces spending redeemers with index0..n−1 and public datum I0; empty input leaves the original transaction unchanged. Return actual `transaction_cbor_hex`, `ledger_size`, `minimum_fee`, `execution_fee`, `reference_script_fee`, `reference_stride` and rational `reference_multiplier`. Ledger size excludes the phase2 validity flag; execution cost aggregates units then ceilings, reference tiers aggregate exact rational costs then floor. This is a fee-calculation profile, not a claim that public fixture UTxOs/redeemers are ledger-admissible.

`time.slot-boundary` accepts `slot_length_picos` (positive u64 <=10^15), `elapsed_picos` (u64), and `epoch_length` (positive u32). The bounded wrapper rejects an elapsed/slot quotient >=u64::MAX. It returns exact `floor_slot`, `ceiling_slot` and `floor_time_picos`; malformed/negative/zero/out-of-bound inputs return invalid_input. The Haskell oracle calls actual wallet Primitive.Slotting ongoingSlotAt/ceilingSlotAt/slotToUTCTime through mkSingleEraInterpreter. Tests cover genesis, a picosecond before/on/after slots and epochs, fractional slot lengths and upper input boundaries. This explicitly single-era component does not establish hard-fork compatibility. Rust independently validates integer quotient/remainder/ceiling and registers the complete frozen corpus. Reproduce capture with `capture-slotting-profiles --oracle <pinned-slotting-helper> --output <new-file>`; existing files cannot be overwritten. Candidate adapters implement the same operation.

The balancing corpus adds actual wallet `transaction.roundtrip` goldens for individually and jointly specified collateral inputs/return/total fields in Babbage and Conway, plus an incomplete Conway payment. `collateral_flags` is immutable fixture context (bits1/2/4), while the actual Haskell decoder consumes the supplied canonical CBOR. `metadata.encrypt` and `metadata.decrypt` use ordered recursive metadata `entries` in the same representation as `metadata.encode`, plus a hexadecimal UTF-8 `passphrase_hex`. Encryption additionally requires an explicit eight-byte `salt_hex` for deterministic conformance captures. Results contain the exact ordered entries returned by the pinned Haskell helper. Structured helper failures expose their Haskell constructor as `error.code`. The exact known msg-before-note decryption ErrorCall is represented as `haskell_error_call` with class `ErrorCall` and its preserved message; arbitrary exceptions still fail the process. `reference/MetadataAdapter.hs` invokes the actual helpers and forces complete JSON output before catching that one failure. Both map orders are mandatory: note-before-msg decrypts successfully; msg-before-note preserves the observed failure. Fixed-salt byte comparison supplements the independent OpenSSL/live-node CIP83 control and does not replace it. Fixture passwords are published test data.
