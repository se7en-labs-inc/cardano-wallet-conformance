# Real local-cluster execution

The Rust suite connects through HTTP. The node/cluster and each wallet service are separate processes, so the candidate's command line can be completely different from cardano-wallet's.

Use a Haskell checkout that provides the `local-cluster` executable, `cardano-node`, `cardano-cli` and its matching `lib/local-cluster/test/data/cluster-configs`. Build/provide these through that checkout's Nix environment. Do not mix node/cluster configuration versions without recording them. The Rust template intentionally does not fetch or rebuild the whole Haskell wallet project.

Start a dedicated cluster in a short absolute path (Unix sockets have path-length limits):

```sh
mkdir -p /tmp/wc-example
printf '%s\n' '{"pureAdaFunds":[],"maryAllegraFunds":[],"massiveWalletFunds":[]}' > /tmp/wc-example/funds.json
LOCAL_CLUSTER_ERA=conway local-cluster \
  --cluster-configs /absolute/path/to/cardano-wallet/lib/local-cluster/test/data/cluster-configs \
  --cluster /tmp/wc-example/cluster \
  --socket-path /tmp/wc-example/node.socket \
  --monitoring-port 8077 \
  --faucet-funds /tmp/wc-example/funds.json
```

The empty extra-funds file is sufficient: the existing cluster separately initializes its internal faucet addresses. The suite calls that service's `POST /send/faucet-assets` endpoint to fund a newly generated sender address. This exercises real node transactions, not an in-memory faucet.

Start the Haskell reference against that node socket and generated Byron genesis:

```sh
cardano-wallet serve \
  --node-socket /tmp/wc-example/node.socket \
  --testnet /tmp/wc-example/cluster/byron-genesis.json \
  --database /tmp/wc-example/reference-db \
  --port 8090 --ui-port 8092 --pool-metadata-fetching none
```

Start the candidate on another HTTP port with its own empty database, configured for the same network magic (42), genesis and node socket. Its launch mechanism is implementation-specific. Wait for its HTTP listener to become available, then use `live --target http://127.0.0.1:8091/v2/ --faucet http://127.0.0.1:8077/ ...`. The suite itself waits for chain synchronization, advancing block height and funded balances.

Run live workflows against reference and candidate separately. Each creates distinct wallets and spends distinct faucet outputs, avoiding double-spends caused by running the same funded mnemonic twice on one chain. For an external testnet, supply distinct funded mnemonic fixtures for separate runs. Use only dedicated test wallets; a funded mnemonic already registered on the service results in a creation failure rather than adopting an existing wallet.

Terminate both wallet processes and the cluster after testing, including on failure. The suite deletes the wallets it created; it does not own externally started processes and does not terminate them. A parent CI supervisor should bracket those process lifetimes. Keep logs outside the repository and retain public, redacted execution reports plus exact binary versions, genesis/protocol parameter records and build hashes.

Live runs also require `--node-socket /tmp/wc-example/node.socket --network-magic 42`, plus a trusted Haskell `cardano-cli` on PATH or `--cardano-cli /absolute/path/to/cardano-cli`. This is an independent node query driver, not the replacement wallet's CLI. The suite verifies block advancement directly and checks that the real node's UTxO set contains the submitted transaction's exact recipient output and amount. Wallet-reported confirmation alone cannot pass that check. For preprod, use its node socket and network magic 1 instead.

Add `--families` to a `live` invocation with a local-cluster faucet to exercise funded random/icarus Byron wallets and a fresh Shelley wallet after the basic transfer/restoration flow. This profile generates fresh mnemonic material, confirms real faucet funds with the node, checks fee estimates and applicable random coin selections, sends payments, then plans and submits complete migrations into an owned Shelley destination. Every migration must conserve ADA against the plan, leave an empty source balance and produce exact independently queried recipient UTxOs. All successfully created wallet families are cleaned up on success or failure. This flag requires a faucet and never adopts an existing funded wallet. It adds genuine node-backed compatibility evidence; it does not yet cover shared multisig, rollback or node disconnection.

The independent `--shared` live profile creates two pending all-of-two wallets, exports and patches reciprocal account keys, and checks matching discovered script addresses and node-backed funds. It verifies the first signature and exact missing-witness403, independently verifies the merged two-signature transaction and the native script hash/key clauses against the funded address, then requires both parties' confirmed history, exact balances and node-confirmed recipient UTxOs. It requires the dedicated local faucet and cleans up the shared wallets it creates.

Use `--external-signer http://127.0.0.1:8090/v2/` with a separate isolated reference wallet service to test a funded account-public-key wallet's external-signing flow. The reference service owns the fresh private fixture; the target owns only its watch wallet and recipient. The profile compares address pools, checks the watch ID against Blake2b160(account public key), rejects target signing with no_root_key403, independently verifies the external witness against the watch address's payment-key hash and unchanged body, and requires target submission, both wallet histories/accounting and exact node outputs. Fixture signer API calls never count as target API evidence. Cleanup runs on both services even when the profile fails. This profile requires the dedicated local faucet.

Use `--assets` with the dedicated faucet to exercise actual wallet-native minting and burning. The profile derives/checks the wallet policy ID independently, mints empty and named tokens, checks inventory/fingerprints and UTxO snapshots, burns all empty-name and part of the named tokens, and reconciles exact signed CBOR quantities and node outputs. A deliberately corrupted policy witness must fail independent verification and actual ledger admission before the valid mint is submitted as binary bytes through `/proxy/transactions`.

The pinned Haskell handler reports actual node witness rejection as500 `created_invalid_transaction`, with the node's `InvalidWitnesses` cause. The original OpenAPI omits this500 response. This supplemental profile checks that exact source behavior independently and records semantic evidence; it does not claim documented-response schema validation for the500 or manufacture a403. The generated draft records this discrepancy explicitly. Normal successful proxy submission still requires its documented202 and response schema.

Declarative HTTP requests can use `raw_body_hex` for exact binary bytes. It defaults to application/octet-stream; body, raw_body and raw_body_hex are mutually exclusive, and malformed hex fails before sending.

`--payments` runs the Shelley portion of the funded-family workflow independently: fee estimation, coin-selection conservation, deprecated create/send payment, complete migration planning/submission and independent node confirmation/accounting. It uses the same assertions and dedicated Shelley faucet funding as the full family profile. It does not execute or change Byron funding. Combine it with `--assets`, `--shared` and `--external-signer` when running the full available live profile.

`--concurrency` funds one owned sender UTxO and releases two different payment constructions and two signed wallet submissions through barriers. It checks exact shared inputs, different body hashes, quantities/fees and independently verified signatures, requires exactly one accepted transaction, confirms the winner and reconciles both wallets. The losing request must match either node500 BadInputsUTxO or the documented403 foreign_transaction outcome after the input has become spent; the exact observed variant is recorded and winning ledger confirmation/accounting is required. A later binary proxy submission of the losing signed transaction must fail with actual node500 BadInputsUTxO naming the shared funding hash. It also verifies internal change discovery, exact node change outputs and wallet snapshots. All other statuses/causes and double acceptance/rejection fail. This profile requires the dedicated local faucet and cleans up all owned wallets.

`--metadata` uses the development shell's OpenSSL (or `--openssl /explicit/path`) to verify CIP83 encryption independently. It checks exact auxiliary hashes/binary CBOR, unrelated labels and64-byte binary values, correct and wrong Shelley decryption, shared ciphertext inspection, real submission and confirmed metadata history/node accounting. Shared decryption is explicitly unimplemented in the pinned handler; this profile does not fabricate its documented403. Original API/correction evidence is retained separately.

`--balance` tests an independently encoded incomplete Conway payment through `/wallets/{id}/transactions-balance`: empty-wallet403, funded202, independent selection/fee/output checks, signing, submission and exact node/wallet accounting. Run it with the dedicated cluster faucet and include its live report alongside the HTTP and all internal reports under the same fingerprint. The new `capture-balancing-profiles` command captures11 actual wallet ledger-codec goldens; replay `fixtures/vectors/balancing-profiles.json` with the pinned ledger reference adapter in every complete internal run.

`--collateral` independently exercises the current Haskell unsupported-collateral guards. Its observed return-code spelling disagrees with the original OpenAPI; the user-approved correction is applied in the hash-guarded behavioral overlay. The profile retains strict schema validation and retains exact error codes and messages. Do not claim collateral-return coverage from codec replay alone.

`--voting` runs stake registration, abstain/no-confidence delegation and retirement/refund with fresh isolated funding, a modern signed-byte control, exact deprecated API certificates/accounting, independent node stake/UTxO queries and actual epoch activation. Allow enough time for several local epochs. Genesis pools are intentionally absent from the wallet executable's pool database; this profile exercises vote delegation independently of pool joining.

The executable intentionally omits genesis pools from its pool database. After the initial HTTP baseline, prepare a pool for staking tests with the independently verified Rust fixture command (use the current owned cluster path):

```sh
cargo run -- prepare-pool-fixture \
  --owned-cluster-pool /tmp/wc-example/cluster/pool-1 \
  --node-socket /tmp/wc-example/node.socket \
  --cardano-cli /explicit/trusted/cardano-cli \
  --target http://127.0.0.1:18790/v2/ \
  --faucet http://127.0.0.1:18777 \
  --output-directory artifacts/pool-fixture-new
```

This command requires magic42, zero pool deposit and an existing node-known pool whose signing keys you explicitly supply from your owned test cluster. It creates fresh CLI payment credentials and faucet funding, re-registers the pool on-chain, independently verifies its certificate, body hash, three signatures, minimum fee, spending/change and wallet visibility. It refuses existing output directories and already visible pools. The default pledge150000000000000 matches the bundled cluster's pool1; specify `--pledge` when using a different owned pool. No wallet source/database is edited. Only `public/` contains shareable evidence and the receipt explicitly does not count as conformance evidence. Keep `private/` under ignored local scratch; it contains the fixture payment signing key. Setup changes the cluster pool list, so run it after HTTP baseline tests or on a separate fixture cluster.

`--input-limits` exercises600independently funded UTxOs, exact preselected-input balance202/oversize403 boundaries and signed/node-confirmed admission of the largest accepted control. It requires the dedicated faucet and the controlled16384-byte protocol maximum. Allow time for six100-output funding transactions and several balance probes. Include `fixtures/vectors/signed-size-profiles.json` through the pinned SizeAdapter and `reward-profiles.json` through LedgerAdapter in the same coherent replay as all prior corpora; the full internal set is1223cases.

For owned crash/restart checks, add `--wallet-launch <manifest.json> --wallet-workspace <new-absolute-directory>` to `live`. The target must be an unused explicit loopback HTTP URL ending in `/v2/`. The JSON manifest has an absolute `executable`, `arguments` array and optional `environment` map. Put the complete string `{database}` in exactly one argument or environment value; for Haskell this is the argument following `--database`. Supply the cluster's node socket/genesis and dedicated service/UI ports as ordinary arguments. The wallet must remain a foreground child. The suite creates the private directory, captures private per-generation logs, starts the service, runs the funded basic workflow, then kills/restarts the same binary against the same database. It verifies exact confirmed state/address/key/UTxO/history projections and deterministic independently verified signing. Only confirmed and key/address restart cases bind; pending persistence remains uncovered. The owned service is stopped and reaped on exit, while its database/logs remain private for inspection. Existing external-service mode is unchanged. Do not run ordinary differential suites against this owned service before startup; a complete coherent run must arrange the HTTP stage separately before funding.

For the separate disconnection scenario, add `--node-disconnect-socket <new-absolute-socket>` alongside the owned launch/workspace flags and dedicated faucet. Its parent must already be private. The launch manifest's node-socket argument must equal this proxy path; `--node-socket` continues to identify the direct trusted node for independent queries. The suite starts the transparent relay, runs the basic transfer/restoration workflow, disconnects all wallet connections, confirms10m of new funding independently while the wallet remains unaware, then reconnects and requires catch-up. A subsequent2m payment must pass signature/input/fee conservation, node confirmation and full balances over every owned wallet address. This explicitly selected scenario runs in place of owned restart; it does not fix or bypass assertions within the separately failing restart profile. Its receipt closes only the disconnect/reconnect named case when all controls pass; pending retry/expiry remain required.

`--history --byron-genesis <cluster/byron-genesis.json> --shelley-genesis <cluster/shelley-genesis.json>` adds independently funded metadata-bearing self-payments and detailed history filter controls. It needs a dedicated faucet and the controlled single-era cluster. The profile validates exact metadata bytes and signed/node-confirmed accounting before testing time/order/max_count/address/minWithdrawal queries. It leaves pending/expired status behavior separate. It can run after the explicit owned disconnection scenario while the original owned restart correction remains pending.

The Linux `verify-pending-state` command requires `--cluster-launch`, `--wallet-launch`, a fresh absolute `--workspace`, pinned `--cardano-node`/`--cardano-cli`, explicit unused loopback `--target`, dedicated `--faucet`, `--environment` and `--report`. Cluster launch uses the existing `{cluster}`, `{socket}`, `{funds}`, `{logs}` placeholders and an explicit PATH containing the pinned node/CLI. Wallet launch uses whole-value `{node_socket}`, `{byron_genesis}`, `{database}`. This workflow exclusively owns every producer and the relay; it never adopts an existing process. It tests pending restart and pending deletion/reappearance, not rollback or expiry.
