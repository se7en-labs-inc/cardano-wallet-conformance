# Executable live-wallet contracts

These contracts describe the assertions shipped with the Rust harness. The pinned Haskell behavior remains authoritative; an exported specification is a review draft. A described profile, a source-supported outcome or an offline harness test is not evidence of live execution. Only the supplied passing reports under the exact current suite fingerprint establish the bounded validation result. Every missing required case or execution failure prevents the644-obligation gate from passing.

The production interface is HTTP. The trusted Haskell cardano-cli is an independent node query driver; wallet CLI compatibility is excluded. Candidate and reference wallet services have separate databases on the same explicitly identified network. Source/environment binding and executable hashes belong in runtime evidence. Published/internal component vectors remain separate proof for exact key derivation, codecs, signatures, fees and seeded selection; a successful live payment cannot replace them.

## Common inputs, accounting and ownership

`live` takes a target API URL, trusted node socket/CLI, network magic, environment and timeout. Basic execution requires exactly one of a dedicated local-cluster faucet or a funded TESTNET mnemonic. Extended profiles require the dedicated faucet. Payment amount is at least2000000 lovelace. New profiles use fresh generated mnemonic material and do not adopt wallets that already exist. The test encryption passphrase is a public fixture, not a user credential.

Each successfully created Shelley, Byron or shared wallet becomes owned immediately upon a201 response with its ID, before further schema assertions. Cleanup attempts deletion of every owned wallet on success and failure. The external signer owns its own fresh private fixture and cleans it independently. Failed cleanup is report evidence and prevents complete conformance. Requests or response bodies, mnemonic material and private keys are excluded from report diagnostics.

For documented API calls, method/path binding, exact expected status and response schema must pass. NoContent responses must be empty. Polling treats transport/schema failures as failures; expected transaction404 while discovery catches up is separately validated. Readiness and balances must reach the required values within the bounded timeout. ADA arithmetic uses checked integer quantities. No failed, unsupported, skipped or unexecuted profile is converted into a pass.

The independent node driver validates advancing block height and exact wallet latest-header hash/height/slot against observed node tips. Payment proof requires node UTxOs with the exact transaction ID, address and total lovelace; native-asset proof additionally reconciles every policy/name/quantity, including empty names, with no unexpected assets. Wallet-reported confirmation alone is insufficient.

## Basic transfer and restoration

The basic profile requires correct network magic, actual block production and independently matching latest headers. It creates a fresh recipient and either restores the explicitly funded sender fixture or creates/funds its own sender. Both wallets must be ready and the sender have adequate available funds.

Construction must return a positive fee and a coin selection conserving inputs = requested outputs + change + fee, with unique inputs and the exact requested amount. Independent CBOR inspection must reproduce the returned body hash, selected input IDs, exact destination and payment amount. Signing with an incorrect passphrase must fail with the pinned error. Successful signing must retain the original body and fee and provide independently valid extended-derived Ed25519 witnesses. Decode and submission IDs must equal the independently computed body hash.

Both source and recipient must discover the confirmed transaction with correct direction, fee and amount. The node must independently confirm the exact recipient output and every change output. Source balance decreases by payment + fee; recipient balance increases by the payment. UTxO snapshot totals and logarithmic histogram bucket counts must match those balances and actual entry amounts.

Deleting and restoring the recipient from the same mnemonic must retain identity, discovered addresses, confirmed balance and transaction fields including inputs, outputs, fee, amount, metadata and insertion data. This proves the shipped restore-from-genesis case; it does not establish restart durability, rollback or restore-from-checkpoint cases.
