# Submission bookkeeping diagnostic

`reference/SubmissionRaceDiagnostic.hs` calls the actual pinned submission implementation. It decodes an actual signed Conway transaction, independently checks its ledger-derived hash against the public captured ID, constructs a pending entry through the production operation, confirms it through the production roll-forward function, then calls the production resubmit bookkeeping and delta application. It implements no submission transition or expected answer. Bounds and input size are checked. This is diagnostic-only evidence and cannot satisfy an HTTP route or wallet obligation.

Build the existing immutable Git-pinned toolchain as documented in reference-credentials.md, then compile with its ghc using `-O1 -Wall -Werror -package aeson -package memory -package delta-types -package cardano-wallet -package cardano-wallet-primitive -package cardano-wallet-read`. Supply JSON on stdin with cbor_hex, transaction_id, expiry, acceptance, tip and retry_slot. The source/executable hashes and exact captured input/output are retained in evidence/reference-duplicate-history-first.

The original reference reports before_delayed_bookkeeping=in_ledger, after_delayed_bookkeeping=pending, and pending_control_after_bookkeeping=pending. This establishes the unsafe production state transition under a delayed callback. The live history response independently exhibits the same transaction ID as both pending and in_ledger; the exact live thread schedule is not established by the pure diagnostic. Neither observation is waived or normalized away, and no corrected reference is promoted.

The separately named module copy under evidence/reference-duplicate-history-first/isolated-proposal contains one proposed current-status guard. The identical diagnostic input now preserves in_ledger and emits zero delayed-bookkeeping operations; ordinary pending bookkeeping remains pending. Both copies compiled with -Wall -Werror through the same pinned Nix toolchain. The standard proposed patch passes git apply --check against the original checkout. Only pure functions were validated: the original checkout and live wallet binary are unchanged, and neither application-level correctness nor the full live fix is claimed.
