# Draft: confirmed transaction appears twice after rollback/reapplication, as pending and in_ledger

Not submitted. Original cardano-wallet revision2fc5c383c94bb907deaa0cd27b1b407f86224b6c, native node11.1.3, CLI11.2.3.0, real isolated Conway branches. No wallet database edits or fabricated node responses.

After a locally confirmed transaction is rolled back, automatically resubmitted and independently confirmed on branch B, GET /v2/wallets/{id}/transactions returns the same ID twice:49e36ef7e699f6c568f05abb5dd5ea0bb8c24a3c9be3e2c2f291364ab518d6b6, once in_ledger and once pending. The wallet reports ready at height302/slot756; native tips surrounding observation are302/756 and304/758. The confirmed row identifies insertion at299/747; the pending row retains pending_since182/382. Both rows occur in the same raw response, and the subsequent normalized snapshot also contains them. Full public responses, signed bytes and native context are retained alongside this draft. A prior fresh run failed the same uniqueness assertion without retaining the rows.

Source-supported mechanism: Wallet.hs3739–3759 reads pending submissions, invokes postSealedTx, then performs resubmitTx atomically. A chain update can confirm the transaction between that earlier read and the bookkeeping call. DB/Store/Submissions/Layer.hs114–128 obtains the current entry without requiring it still be InSubmission, then returns AddSubmission/Forget deltas. An independent thin diagnostic invoking the actual pinned rollForwardTxSubmissions, resubmitTx and production delta application on the real captured signed transaction proves in_ledger→pending after delayed bookkeeping. Its ordinary pending control stays pending. This proves the unsafe state-machine interleaving, not the exact thread schedule of the live reproduction.

DB.hs380–412 concatenates ledger history with pending/expired submissions without deduplicating transaction IDs. Thus inconsistent submission state can produce the observed two rows. Expected invariant: a stale resubmission callback must preserve an already confirmed state, and the history endpoint must return unique transaction identities. A possible narrow correction is to apply bookkeeping only when the current submission is still InSubmission. Guarding only the API merge could hide the underlying submission-state defect and repeated retries.

The strict conformance failure remains in place. A quiescent follow-up and correction validation are still pending. This draft is not a claim that a patch is live-validated or that the precise live interleaving is proven.

The copied actual module and same diagnostic compile with -Wall -Werror; the identical captured input now yields in_ledger→in_ledger with zero callback operations, while the ordinary pending control remains pending. The patch passes read-only applicability checking against the original source. Full application/live validation and quiescent follow-up remain pending; no corrected runtime or source authority was substituted.
